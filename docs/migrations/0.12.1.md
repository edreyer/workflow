# Upgrading to v0.12.1

0.12.1 fixes bugs and adds a tutorial. The public API is unchanged, so code that compiles against 0.12.0 compiles against 0.12.1 without changes. No dependencies changed.

## `mapError` Now Sees Every Error

In 0.12.0, two combinators raised their errors past an enclosing `mapError`, so the use case received the unmapped error:

```kotlin
val chargeCard = workflow<PricedOrder, PaidOrder, PaymentError>("charge-card") { ... }
  .retry(transient)
  .mapError { OrderError.PaymentFailed(it) }

val prepare = parallelJoin(loadCustomer, priceItems) { customer, total -> ... }
  .mapError { OrderError.Lookup(it) }
```

When the retries ran out, or a branch of the join failed, the `errors` mapper received a `PaymentError` or a branch error typed as an `OrderError`. Its `when` then failed with a `ClassCastException`, which propagated to the caller. In 0.12.1 the mapper receives the mapped error, as the types promise.

If you worked around this, remove the workaround. For example, a step wrapped in `recover` only to turn the error into another type now has nothing left to do:

```kotlin
// Before: recover used instead of mapError around the retry
.retry(transient)
.recover { _, error -> raise(OrderError.PaymentFailed(error)) }

// After
.retry(transient)
.mapError { OrderError.PaymentFailed(it) }
```

The inline `Pipeline.parallelJoin(...)` and steps without `retry` or a top-level `parallelJoin` were not affected.

## Summaries Name The Failing Branch

When `mapError` or `recover` wrapped a top-level `parallelJoin`, `UseCaseSummary.rootError.workflowId` named the join, such as `parallelJoin(load-customer,price-items)`. It now names the branch that failed, such as `load-customer`, as it already did for a join without a wrapper. If you alert or count on that field, expect the branch id.
