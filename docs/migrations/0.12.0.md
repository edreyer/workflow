# Upgrading from v0.10 to v0.12

0.11.0 and 0.12.0 are additive, so code that compiles against 0.10 compiles against 0.12 without changes. This guide covers the two deprecations you may see, the dependency changes, and the hand-written code that the new features can replace. The deprecated APIs are removed in 1.0.

## Deprecations

### `WorkflowContext.LAUNCHED_FAILURES`

The context holds only what the caller passed, so launched failures moved out of it. The library still fills the key until 1.0. The messages are the same in every form.

```kotlin
// Before
val failures = context[WorkflowContext.LAUNCHED_FAILURES].orEmpty()

// After, in an onSummary listener
val failures = summary.launchedFailures

// After, in result { }
val failures = events.filterIsInstance<LaunchedFailureEvent>().map { it.message }
```

### `WorkflowExecution.workflowName`

It has always equalled `workflowId` since 0.10, so read `workflowId` instead.

```kotlin
// Before
summary.executions.map { it.workflowName }

// After
summary.executions.map { it.workflowId }
```

## Dependency changes

- 0.11 adds `kotlinx-coroutines-slf4j` as an `implementation` dependency. It keeps the correlation ID in the SLF4J MDC.
- 0.12 adds `arrow-resilience` as an `api` dependency, versioned by the Arrow BOM, because `retry` takes an Arrow `Schedule`. If you import a different Arrow version yourself, keep `arrow-core` and `arrow-resilience` on the same version.

## Behavior to know about

- While a use case runs, `WorkflowContext.CORRELATION_ID`, when it is set, is in the SLF4J MDC under the key `correlationId`. If your application already puts its own value under that key, the use case's value is used during the run, and your value is restored afterwards.

## Code you can replace

None of these changes is required.

| In 0.10 you wrote | From 0.11 or 0.12 |
| --- | --- |
| `withTimeoutOrNull(2.seconds) { payments.capture(order) } ?: raise(PaymentError.TimedOut)` inside a step | `chargeCard.timeout(2.seconds) { PaymentError.TimedOut }` (0.12) |
| A retry loop inside a step | `chargeCard.retry(schedule)` with an Arrow `Schedule<Failure<E>, *>`, which keeps only the successful attempt's events (0.12) |
| `recover({ ... }) { error -> ... }` inside a step, wrapping a reusable step | `chargeCard.recover { input, error -> ... }` (0.12) |
| A step that copies part of the state in and merges its result back by hand | `.then(step, input = { it.order }) { out -> copy(field = out) }` (0.11) |
| A lambda that only adapts a reusable step's input or output type | `step.mapInput { ... }` and `step.mapOutput { ... }` (0.11) |
| A `timeout` on every `thenLaunch` | `useCaseConfig { launchTimeout(5.seconds) }` as the default (0.11) |
| The same sequence of steps repeated across use cases | A reusable `pipeline<S, E>()` added with `.then(pipeline)` (0.11) |
| A step whose block chooses between two other steps | `.branch(ifTrue, ifFalse) { predicate }` (0.11) |

See the [reference](../reference.md) and the [CHANGELOG](../../CHANGELOG.md) for each feature.
