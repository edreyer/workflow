# Migrating to v0.9.0 Typed Pipelines

v0.9.0 makes the use case pipeline type-checked. In 0.8.x, any `then(...)` compiled, and a step whose input did not match the previous step's output failed at runtime with a `CompositionError`. In 0.9.0 the compiler checks every step against the state before it.

Getting there required breaking changes. They all follow from four decisions:

1. **Pipelines are chained.** `startWith` returns a `Pipeline<I, E, S>`, and each step returns a new pipeline with the next state type. Finishing with `.result { }` is what makes it a use case.
2. **Steps use Arrow's `Raise`.** Workflows and `startWith` return plain values and fail with `ensure`, `raise`, or `bind()`. You no longer build `Either` or `WorkflowResult` values by hand.
3. **Errors are not wrapped.** The error a step raises reaches your `errors` mapper unchanged, and it can be your own type.
4. **Less ceremony.** Marker interfaces, string context keys, reflection and several redundant APIs are removed.

## Checklist

| 0.8.x | 0.9.0 |
| --- | --- |
| `useCase { startWith {...}; then(a); then(b); result(state<S>()) {...} }` | `useCase { startWith {...}.then(a).then(b).result {...} }` |
| `startWith { Either.Right(state) }` | `startWith { state }`, fail with `ensure`/`raise` |
| `class X : Workflow<I, O>() { override suspend fun executeWorkflow(input) = ... }` | `class X : Workflow<I, O> { override suspend fun WorkflowStepScope.execute(input: I): O }` |
| `Either.Right(WorkflowResult(state, events, context))` | `emit(event)`, `put(key, value)`, `return state` |
| `error is ExecutionContextError` / `error.rootCause()` | Match the error directly |
| `: WorkflowState`, `: UseCaseCommand` | Remove (deprecated, no longer needed) |
| `result(state<S>()) { s -> }` | `.result { s -> }` |
| `result(event<E>()) { e -> }` | `.result { requireEvent<E>() }` |
| `result(UseCaseResultProjection { r, name -> })` | `.result { s -> }` with `events` and `context` in scope |
| `thenIf(w) { result -> }` | `.thenIf(w) { state -> }`, with `events`/`context` in scope |
| `parallel<S> { then(a); then(b) }` | `.parallel(a, b)` |
| `parallelJoin(a, b, ParallelErrorPolicy.FailFast) { x, y -> }` | `.parallelJoin(a, b, policy = ParallelErrorPolicy.FailFast) { x, y -> }`, input available as `this` |
| `thenLaunch(w, timeout = Duration.ofSeconds(2))` (java.time) | `.thenLaunch(w, timeout = 2.seconds)` (kotlin.time) |
| Launched work lost without `awaitLaunched()` | Launched work is always merged before `result` |
| `Key.string("x")`, `addData`, `get`, `getTypedData` | `Key<String>("x")`, `with`, `context[key]` |
| `workflowUseCase { }`, `executeDetailed`, `executeForState`, `executeForEvent` | `useCase { ... .result { } }` (see below) |
| `logging { success(state<S>()) { s -> } }` inside the block | `.logging { success { result -> } }` chained after `.result` |
| `result.toSummary(useCaseName = ...)` | `useCaseLoggingGlobalConfig { onSummary { summary -> } }` |
| `workflow.execute(input, context)` | `workflow(input, context)` |

The rest of this guide shows each change with a before and after.

## Use Case Pipelines

Before:

```kotlin
val processOrder: UseCase<ProcessOrderCommand, ApiError, OrderReceipt> =
  useCase(name = "ProcessOrder", errors = ::toApiError) {
    startWith { command ->
      Either.Right(OrderDraft(command.orderId, command.items, command.paymentToken))
    }

    then(ValidateOrder())

    parallelJoin(CalculateSubtotal(), CalculateTax()) { subtotal, tax ->
      PricedOrder(subtotal.order, subtotal.amount, tax.amount)
    }

    parallel<PricedOrder> {
      then(CheckInventory())
      then(CapturePayment())
    }

    thenIf(PrepareShipment()) { result ->
      result.context.getTypedData<Boolean>("inventoryAvailable") == true
    }

    thenLaunch(SendConfirmation())
    awaitLaunched()

    result(state<PricedOrder>()) { order ->
      OrderReceipt(order.order.orderId, order.total)
    }
  }
```

After:

```kotlin
val processOrder: UseCase<ProcessOrder, ApiError, OrderReceipt> =
  useCase(name = "ProcessOrder", errors = ::toApiError) {
    startWith { command -> OrderDraft(command.orderId, command.items, command.paymentToken) }
      .then(validateOrder)
      .parallelJoin(calculateSubtotal, calculateTax) { subtotal, tax ->
        PricedOrder(order = this, subtotal = subtotal.amount, tax = tax.amount) // `this` is the ValidatedOrder
      }
      .parallel(CheckInventory(), CapturePayment())
      .thenIf(prepareShipment) { context[Keys.INVENTORY_AVAILABLE] == true }
      .thenLaunch(sendConfirmation)
      .result { order ->
        OrderReceipt(order.order.orderId, order.total, events.lastEvent<ShipmentPrepared>()?.trackingNumber)
      }
  }
```

What changed:

- Each call returns a new `Pipeline`, so `.then(validateOrder)` only compiles if `validateOrder` accepts an `OrderDraft`. Putting the steps in the wrong order is now a compile error instead of a runtime `CompositionError`.
- The block must return the result of `.result { }`, so forgetting the result projection is also a compile error. The 0.8.x runtime checks on `startWith` (called once, called first) are gone, because the pipeline starts at `startWith` by construction.
- `.result { }` receives the typed final state. It no longer needs `state<PricedOrder>()` to look the type up.
- `awaitLaunched()` before the end is no longer needed. See [Launched Side Effects](#launched-side-effects).

The full example is in [`OrderProcessingExampleTest.kt`](../../src/test/kotlin/io/liquidsoftware/workflow/OrderProcessingExampleTest.kt).

Kotlin needs the input type to type the `startWith` lambda. Give the use case an explicit type, as above, or pass the type arguments: `useCase<ProcessOrder, ApiError, OrderReceipt>(name = "ProcessOrder", errors = ::toApiError) { ... }`.

## Workflow Steps

`Workflow` is now an interface with one method. It runs inside a `WorkflowStepScope`, which is an Arrow `Raise<WorkflowError>`, so a step returns its new state and fails by raising.

Before:

```kotlin
class ValidateOrder : Workflow<OrderDraft, ValidatedOrder>() {
  override val id = "validate-order"

  override suspend fun executeWorkflow(
    input: OrderDraft,
    context: WorkflowContext,
  ): Either<WorkflowError, WorkflowResult<ValidatedOrder>> = either {
    ensure(input.items.isNotEmpty()) { WorkflowError.ValidationError("Order has no items") }
    WorkflowResult(
      state = ValidatedOrder(input.orderId, input.items),
      events = listOf(OrderValidated(UUID.randomUUID(), Instant.now(), input.orderId)),
      context = context.addData("validatedAt", Instant.now()),
    )
  }
}
```

After:

```kotlin
class ValidateOrder : Workflow<OrderDraft, ValidatedOrder> {
  override val id = "validate-order"

  override suspend fun WorkflowStepScope.execute(input: OrderDraft): ValidatedOrder {
    ensure(input.items.isNotEmpty()) { OrderError.EmptyOrder }
    emit(OrderValidated(input.orderId))
    put(Keys.VALIDATED_AT, Instant.now())
    return ValidatedOrder(input.orderId, input.items)
  }
}
```

Or, when the step does not need its own class:

```kotlin
val validateOrder = workflow<OrderDraft, ValidatedOrder>("validate-order") { draft ->
  ensure(draft.items.isNotEmpty()) { OrderError.EmptyOrder }
  emit(OrderValidated(draft.orderId))
  ValidatedOrder(draft.orderId, draft.items)
}
```

What changed:

- Drop the `()` after `Workflow<I, O>`; it is an interface now.
- Replace both `executeWorkflow` overloads with `override suspend fun WorkflowStepScope.execute(input: I): O`. In 0.8.x, forgetting to override either overload compiled and then failed at runtime.
- Return the state. Use `emit(event)` for events and `put(key, value)` for context data. `context` is available as a property.
- Errors: `ensure`, `ensureNotNull`, `raise`, and `someEither.bind()` work directly. Thrown exceptions still become `WorkflowError.ExceptionError`, and so does a timeout the step starts itself with `withTimeout`, which no longer cancels the whole use case.
- Steps no longer need reflection to find their input type, so the library no longer depends on `kotlin-reflect`.

## Errors

### Errors are no longer wrapped

In 0.8.x every step failure was wrapped in `WorkflowError.ExecutionContextError`, so a mapper that matched `is DomainError` silently fell through to `else`. In 0.9.0 the mapper receives the error exactly as it was raised. `ExecutionContextError` and `ChainError` are removed.

Before:

```kotlin
errors = { error ->
  when (val cause = error.rootCause()) {
    is WorkflowError.DomainError -> ApiError(422, cause.code)
    else -> ApiError(500, "internal")
  }
}
```

After:

```kotlin
errors = { error ->
  when (error) {
    is WorkflowError.DomainError -> ApiError(422, error.code)
    else -> ApiError(500, "internal")
  }
}
```

`rootCause()` still compiles and returns the error unchanged, with a deprecation warning.

The failing step's id is still recorded. It is in `UseCaseSummary.rootError.workflowId`, rather than on the error.

### Your own error types

`WorkflowError` is now an open interface, so domain failures no longer have to be squeezed into `DomainError(code: String, metadata: Map<String, String>)`. Define a sealed hierarchy and raise it from any step:

```kotlin
sealed interface OrderError : WorkflowError {
  data object EmptyOrder : OrderError
  data class PaymentDeclined(val reason: String) : OrderError
}

fun toApiError(error: WorkflowError): ApiError =
  when (error) {
    OrderError.EmptyOrder -> ApiError(400, "empty-order")
    is OrderError.PaymentDeclined -> ApiError(402, "payment-declined")
    is WorkflowError.ValidationError -> ApiError(400, "invalid")
    else -> ApiError(500, "internal")
  }
```

Every error has a `code`, which defaults to its class name, and a `message`, which defaults to its code. Summaries use `code` and redact `message` unless you opt in.

`CompositionError` no longer carries an exception: `CompositionError(message)`. It now only comes from `requireEvent<T>()`, because type mismatches between steps can no longer happen.

## Marker Interfaces

Any type can be use case input or workflow state. `WorkflowState` and `UseCaseCommand` are deprecated and no longer used as bounds.

Before:

```kotlin
data class RegisterUserCommand(val email: String) : UseCaseCommand
data class RegistrationDraft(val email: String) : WorkflowState
```

After:

```kotlin
data class RegisterUserCommand(val email: String)
data class RegistrationDraft(val email: String)
```

Existing classes that still implement the markers keep compiling, with a deprecation warning, so you can remove them gradually.

## `startWith`

`startWith` returns the initial state directly and fails by raising.

Before:

```kotlin
startWith { command ->
  if (command.email.isBlank()) {
    Either.Left(WorkflowError.ValidationError("Email is required"))
  } else {
    Either.Right(RegistrationDraft(command.email))
  }
}
```

After:

```kotlin
startWith { command ->
  ensure(command.email.isNotBlank()) { WorkflowError.ValidationError("Email is required") }
  RegistrationDraft(command.email)
}
```

If you already have an `Either`, call `.bind()` on it.

## Result Projection

`.result { }` replaces `result(state<T>())`, `result(event<T>())`, and `UseCaseResultProjection`. Its block receives the typed final state. Its receiver is a `ResultScope`, which is also a `Raise`, and exposes `events`, `context`, and `requireEvent<T>()`.

| Before | After |
| --- | --- |
| `result(state<RegisteredUser>()) { s -> s.toDto() }` | `.result { s -> s.toDto() }` |
| `result(event<UserRegistered>()) { e -> e.toDto() }` | `.result { requireEvent<UserRegistered>().toDto() }` |
| `result(UseCaseResultProjection { r, name -> r.requireState<S>(name).map { ... } })` | `.result { s -> ... }` using `events` and `context` |

`requireEvent<T>()` raises `CompositionError` when no event of that type was emitted, like `event<T>()` did. Use `events.lastEvent<T>()` when the event is optional.

## Conditional Steps

The predicate receives the typed state. The events and context so far are available through its receiver. Because the step may be skipped, it must return the same state type.

Before:

```kotlin
thenIf(ApplyInviteCode()) { result ->
  result.context.get(INVITE_CODE) != null
}
```

After:

```kotlin
.thenIf(applyInviteCode) { registration ->
  context[INVITE_CODE] != null && registration.email.endsWith("@example.com")
}
```

## Parallel Side Effects

Before:

```kotlin
parallel<PaidOrder> {
  then(SendReceiptEmail())
  then(PublishPaymentEvent())
}
```

After:

```kotlin
.parallel(sendReceiptEmail, publishPaymentEvent)
```

Side-effect steps no longer have to return their input (`Workflow<S, S>`). Any `Workflow<S, *>` works, and its output is ignored. You can also pass `policy = ParallelErrorPolicy.FailFast`.

## Parallel Joins

The merge function now receives the current state as `this`. 0.8.x only passed the branch outputs, so branch states often had to copy every input field just to carry it to the merge.

Before:

```kotlin
parallelJoin(CalculateSubtotal(), CalculateTax(), ParallelErrorPolicy.FailFast) { subtotal, tax ->
  // SubtotalState had to repeat orderId, customerId, items, ... so they could be copied here.
  PricedOrder(subtotal.orderId, subtotal.customerId, subtotal.items, subtotal.amount, tax.amount)
}
```

After:

```kotlin
.parallelJoin(calculateSubtotal, calculateTax, policy = ParallelErrorPolicy.FailFast) { subtotal, tax ->
  PricedOrder(order = this, subtotal = subtotal.amount, tax = tax.amount)
}
```

The policy is now a named parameter that defaults to `WaitAll`. A positional policy still compiles. The top-level `parallelJoin(a, b) { ... }`, which builds a reusable `Workflow`, works the same way.

## Launched Side Effects

Before:

```kotlin
thenLaunch(SendWelcomeEmail(), timeout = Duration.ofSeconds(2)) // java.time.Duration
then(ContinueMainFlow())
awaitLaunched() // without this, launched events and failures were silently dropped
```

After:

```kotlin
.thenLaunch(sendWelcomeEmail, timeout = 2.seconds) // kotlin.time.Duration
.then(continueMainFlow)
```

What changed:

- The timeout is a `kotlin.time.Duration`.
- In 0.8.x the use case already waited for launched work before returning, because the work runs in the use case's coroutine scope. But without `awaitLaunched()` its events and failures were thrown away. Now any launched work still pending is merged just before `.result { }`. `awaitLaunched()` is only needed when a later step must see that work.
- `LaunchedFailureEvent.workflowId` names the launched workflow, and the message comes from the raised error.
- Cancelling the caller cancels launched work. In 0.8.x it was reported as a timeout.
- When launched work is merged, only the context keys it changed are applied, so keys it left alone keep any newer value a later step set. If both changed the same key, the launched value is merged last and wins. Parallel branches merge the same way, in parameter order.

## Workflow Context

Keys are compared by identity, carry their full generic type, and the string-keyed API is removed.

Before:

```kotlin
val TENANT = Key.string("tenant")
val FLAGS = Key.of<List<String>>("flags") // stored List::class, so the element type was erased

val context = WorkflowContext()
  .addData(WorkflowContext.CORRELATION_ID, "corr-123")
  .addData(TENANT, "acme")
  .addData("inventoryAvailable", true)

context.get(TENANT)
context.getTypedData<Boolean>("inventoryAvailable")
```

After:

```kotlin
object Keys {
  val TENANT = Key<String>("tenant")
  val FLAGS = Key<List<String>>("flags")
  val INVENTORY_AVAILABLE = Key<Boolean>("inventoryAvailable")
}

val context = WorkflowContext.of(
  WorkflowContext.CORRELATION_ID to "corr-123",
  Keys.TENANT to "acme",
)

context[Keys.TENANT]
context[Keys.INVENTORY_AVAILABLE]
```

| Before | After |
| --- | --- |
| `Key.string("x")`, `Key.of<T>("x")`, `Key(id, T::class)` | `Key<T>("x")`, declared once and shared |
| `context.addData(key, value)` | `context.with(key, value)`, or `put(key, value)` inside a step |
| `context.get(key)` | `context[key]` |
| `addData(String, Any)`, `getTypedData<T>(String)` | Removed; declare a `Key` |
| `context.combine(other)` | `context + other` |
| `context.executions`, `addExecution` | Removed from the context; see `UseCaseSummary.executions` |

`key to value` builds a typed `Key.Entry`, so `WorkflowContext.of(Keys.TENANT to 42)` is a compile error. If you used `key to value` to build a `Pair` elsewhere, write `Pair(key, value)`.

## Lower-Level Workflow Use Cases

`workflowUseCase`, `WorkflowUseCase`, `UseCaseResult`, `UseCaseEvents`, and the `executeDetailed`/`executeForState`/`executeForEvent`/`executeProjected` methods are removed. `useCase` covers each case:

| Before | After |
| --- | --- |
| `workflowUseCase<C> { ... }.executeForState<S>(command)` | `useCase<C, S> { ... .result { it } }` |
| `.executeForEvent<E>(command)` | `.result { requireEvent<E>() }` |
| `.execute(command)` (events only) | `.result { events }` |
| `.executeDetailed(command)` | `.result { result }` (the `WorkflowResult` with state, events, and context) |
| `.executeProjected(command) { r -> ... }` | `.result { s -> ... }` |

## Logging

Per-use-case logging is chained after `.result { }`, so it knows the final state type. Success fields receive the final `WorkflowResult`, which can be destructured.

Before:

```kotlin
useCase(name = "RegisterUser", errors = ::toRegisterUserError) {
  startWith { command -> Either.Right(RegistrationDraft(command.email, command.password)) }
  then(CreateUserWorkflow(users))
  result(state<RegisteredUser>()) { state -> RegisterUserResponse(state.id) }

  logging {
    success(state<RegisteredUser>()) { state -> field("userId", state.id) }
    success(event<UserRegisteredEvent>()) { event -> field("eventId", event.id) }
    failure { error: RegisterUserError -> field("reason", error.reason) }
  }
}
```

After:

```kotlin
useCase(name = "RegisterUser", errors = ::toRegisterUserError) {
  startWith { command -> RegistrationDraft(command.email, command.password) }
    .then(createUser)
    .result { state -> RegisterUserResponse(state.id) }
    .logging {
      success { (state, events) ->
        field("userId", state.id)
        field("eventId", events.lastEvent<UserRegisteredEvent>()?.id)
      }
      failure { error -> field("reason", error.reason) }
    }
}
```

The global `useCaseLoggingGlobalConfig { ... }` options are unchanged.

## Summaries

`toSummary(...)` is removed, because there is no longer a detailed result to call it on, and it could not see which step failed once errors stopped being wrapped. Register a listener instead. It is called after every invocation:

Before:

```kotlin
val detailed = workflowUseCase.executeDetailed(command)
metrics.record(detailed.toSummary(useCaseName = "RegisterUser"))
```

After:

```kotlin
useCaseLoggingGlobalConfig {
  onSummary { summary -> metrics.record(summary) }
}
```

`UseCaseSummary.duration` is a `kotlin.time.Duration`, measured with a monotonic clock. `RootErrorInfo` gains `code` and keeps `workflowId`. Messages are redacted by default. `summary.withErrorMessages()` replaces `includeErrorMessages = true`.

`WorkflowExecution` gains a monotonic `duration`. Its `startTime` and `endTime` are kept for display.

## Testing a Step on Its Own

Before:

```kotlin
val result = ValidateOrder().execute(draft, WorkflowContext())
```

After:

```kotlin
val result: Either<WorkflowError, WorkflowResult<ValidatedOrder>> = validateOrder(draft)
```

## Build and Compatibility

- Published artifacts target Java 17. 0.8.0's Gradle metadata required Java 25.
- `kotlin-reflect`, `jsoup`, `arrow-fx-coroutines`, and `arrow-resilience` are no longer dependencies.
- The public API is checked with Kotlin's ABI validation (`api/workflow.api`), and the library is compiled in explicit API mode.

## Removed APIs

- `workflowUseCase`, `WorkflowUseCase`, `WorkflowChainBuilderFactory`, `UseCaseResult`, `UseCaseEvents`, `EventOnlyState`
- `state<T>()`, `event<T>()`, `StateResultSource`, `EventResultSource`, `UseCaseResultProjection`
- `ParallelSideEffectScope`, `SideEffectWorkflow`
- `WorkflowError.ExecutionContextError`, `WorkflowError.ChainError`
- `WorkflowUtils`, `Workflow.inputClass`
- `WorkflowResult.mergePrevious`, `WorkflowResult.toUseCaseResult`, `getFromEvent`
- `WorkflowContext.addData`, `getTypedData`, `combine`, `addExecution`, `executions`, `Key.of`, `Key.string`, and the other `Key` helpers
- `toSummary`
